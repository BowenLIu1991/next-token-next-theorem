## 当前 S36 补充 · Harness 实例：Claude Code 代码审查

> 本条使用现行 50 页 deck 页码；下文其他页码为历史稿。

- 来源：Osmani、Lunt、Wang，[*How the Claude Code team does code review*](https://claude.dev/blog/solving-code-review-at-anthropic/)，2026-10-15。
- 讲法：用一个团队自述的工程案例，把 Harness 讲具体，供学术同行参考；具体领域迁移由听众判断。
- 提交前：运行测试、构建或界面检查，展示输出；新上下文的 Agent 审查；项目规则与审查标准来自 CLAUDE.md / REVIEW.md。
- 提交后：AI 审查和问题复核、安全审查、自动测试；按变更风险安排人工审批。多 Agent 一致仅作过滤发现的手段。
- 发布后：分阶段发布、快速发现与回滚，每次变更由人承担责任。
- 积累：历史事故经工程师确认后加入每日评测集；重复问题沉淀为规则、Skill 或可执行检查，同时衡量误报与审查轮数。
- 循环边界：三轮后请作者重新考虑方案，后续聚焦新增变更，避免重复发现造成无限修复循环。
- 收束：把失败沉淀为可复用的检查，让审查经验持续复利。

## 0. 开场（2 页）

### S1 · 封面

**标题**：从下一个 token 到下一个定理
**副标题**：一个模型如何工作，以及我如何使用它
**画面**：一行被切成 token 的句子，右侧是同一句话对应的整数序列。

---

### S2 · 模型看到的是什么

**标题**：这句话，模型看到 10 个整数

```
Celestial mechanics is the poetry of orbits.
→ 10 tokens
→ [69126, 90010, 52347, 382, 290, 38153, 328, 503, 24043, 13]
```

**讲稿要点**：

- 不是字母，不是单词，是一串整数。
- 今天三个问题：这一串整数怎么来的？它怎么预测下一个？我们怎么用它干活？
- 最后回答：为什么这能通向定理。

## 1. Token（7 页）

### S3 · 切分

**标题**：token 是切出来的，不是天生的

```
"三体问题 is a classic problem in celestial mechanics."
→ ["三","体","问题"," is"," a"," classic"," problem"," in"," celestial"," mechanics","."]
→ [3236, 7074, 28917, 382, 261, 13686, 4792, 306, 134437, 52347, 13]
```

**讲稿要点**：

- 切分规则来自一个固定的词表。
- 常见组合占一个 token，生僻组合被拆开：`celestial` → `cel` + `estial`。
- 空格常是 token 的一部分：`" is"`、`" a"` 都带前导空格。
- 中文不总是"一字一 token"。
- **英文经验值**：1 token ≈ 4 字符 ≈ 0.75 词；平均单词约 5 字符，所以 1 词 ≈ 1.3 token。
- **常见词表**：5 万–20 万。GPT-2 50k、GPT-4 100k、Llama 3 128k、GPT-4o 200k。
- **为什么是子词**：字母级信息太少、序列长 4–5 倍；词级词表会爆炸（百万级）；子词是折中。

---

### S4 · 词表

**标题**：词表是一张固定的映射表
**画面**：左侧账本，按 ID 排序，列是 `ID | 片段`；高亮 `28917 问题`，标注「本次查询」。右侧竖直标尺：0 → 50k → 100k → 128k → 200k，顶部大数字 200,019。

**画面底部**：`200,019 × 4,096 ≈ 8.2 亿参数`

**讲稿要点**：

- 词表就是一张索引表：**ID 是行号，片段是那一行的内容**。训练前定好，之后不变。
- 里面不只有"词"：词根、带空格的片段、标点、数字块、多语言片段，还有特殊 token。
- 特殊 token 是控制字符：文本结束、对话角色、工具调用。它们也占一行。
- 词表是模型的字母表：输入的 embedding 按行号取行，输出的 softmax 也在这些行上。
- 算一笔账：20 万行 × 4096 维 ≈ 8 亿参数，光输入和输出这两层就这么多。
- 词表固定 → 没有"未登录词"，新词只能拆成已知片段；代价是序列变长。
- **换模型就是换词表**，同一个 ID 在不同模型里指向不同片段，不能移植。

---

### S5 · 词表是怎么来的

**标题**：不是人编的，是从语料统计出来的
**画面**：BPE 合并过程：`e` + `s` → `es` → `est` …

**讲稿要点**：

- 从 256 个字节开始，反复合并语料里最高频的相邻对。
- 合并多少次，词表就有多大——这是一个人为选的超参数。
- 所以词表带着语料的偏见：中文、代码、数学符号的覆盖取决于训练语料。
- 常见词变成单 token，生僻词保持碎片化。

**一句对比**：

| 粒度 | 词表大小 | 问题 |
|---|---|---|
| 字符/字节 | 256 | 序列太长 |
| 单词 | 百万级 | 生僻词无法表示 |
| 子词 | 5 万–20 万 | 折中 |

---

### S6 · token 不是字，也不是词

**标题**：三个容易踩的坑
**画面**：实测数据

| 类型 | 现象 | 后果 |
|---|---|---|
| 中文 | 同一句 15 字，gpt2 切 28 个 token，o200k 只切 13 个 | 换模型成本差一倍 |
| 数字 | `1234567890` → `123` + `456` + `789` + `0` | 逐位算术容易错 |
| 代码 | 三个空格缩进单独占一个 token | 长代码很快吃满窗口 |

**讲稿要点**：

- token 是"统计上高效的切分"，不是"语义单位"。
- 模型数不对字母、做不好竖式，不奇怪：它没看到字符。
- 同一个模型换 tokenizer，这些表现都会变。

---

### S7 · 三个 token

**标题**：同一个词，三件事

| 名称 | 是什么 | 用在哪 |
|---|---|---|
| 模型 token | 序列的基本单位 | 前向传播、上下文窗口 |
| 计费 token | 同一个单位，按 tokenizer 计数 | API 账单、限流 |
| 认证 token | 一串凭证字符串（API key） | 登录、鉴权 |

**讲稿要点**：

- 前两个是同一个东西的两种用途。
- 第三个只是重名，和文本毫无关系。
- 很多人说"token 用完了"，其实是额度、限流或上下文窗口。

---

### S8 · token 账本

**标题**：窗口、价格、缓存
**画面**：一张账单示意

```
输入：  80,000 token × $2.5/M   = $0.20
输出：   2,000 token × $10/M    = $0.02
缓存命中：60,000 token × $1.25/M = $0.075
```

**讲稿要点**：

- 上下文窗口 = 输入 + 输出的上限。
- 输出通常比输入贵 3–5 倍，因为要逐 token 生成。
- 缓存命中更便宜，适合反复发送同一份长文档。
- 不同 tokenizer 下，同一段文本的 token 数可能差 30% 以上。

> ⚠️ 价格按报告当日更新，不写死。

---

### S9 · 实践含义

**标题**：token 决定了三件事
**画面**：钱、窗口、能力三个图标。

**讲稿要点**：

- **成本**：长文档不要每次重发，用检索或摘要。
- **窗口**：代码和中文更"占地方"，要留余量。
- **能力**：数数、拼写、逐位运算的失败，根源在切分。
- 一句话：token 是模型世界的"像素"。

## 2. 模型（3 页）

### S10 · 它就是一个函数

**标题**：输入 token，输出概率

```
token 序列 → [ Transformer ] → 词表上每个 token 的概率
```

**画面**：黑箱，左边进 token 序列，右边出一条概率条。

**讲稿要点**：

- 沿用李宏毅课程的讲法：机器学习就是在找一个函数；ChatGPT 就是一个超大函数。
- 输入是一串 token，输出是词表上每个 token 的概率。
- 中间是 Transformer：很多层矩阵运算，今天不展开。
- 关键：它不查数据库，也不"理解"；它在算一个分布。

---

### S11 · 自回归

**标题**：一次只吐一个 token
**画面**：取一个 → 接回输入 → 再算 → 循环。

**讲稿要点**：

- 从概率分布里取一个 token（采样或取最大），拼回输入，再算下一个。
- 所以输出是一个一个"蹦"出来的；长文本 = 很多次前向传播。
- 温度、top-p 决定怎么取；同一个 prompt 结果不同，是正常的。
- 内部细节都在备份页，今天不占用时间。

---

### S12 · 无状态

**标题**：每次调用都是全新的
**画面**：两次 API 调用并排，第二次并不"记得"第一次。

**讲稿要点**：

- 模型参数在推理时不更新，每次调用互相独立。
- 所谓"对话"，是客户端把历史消息重新发一遍。
- 单次前向：没有验证、没有记忆、没有分布外保证。
- 记住这句：**模型无状态，记忆是产品。**
- 过渡：这个函数是怎么被训练出来的？

## 3. 训练（9 页）

### S13 · 三个阶段

**标题**：知识、行为、能力
**画面**：一条流水线 + 一张对照表

| 阶段 | 数据 | 目标 |
|---|---|---|
| Pretrain | 互联网文本 | 预测下一个 token |
| SFT | (指令, 回答) | 预测下一个 token |
| RLHF | 人类偏好 | 最大化偏好奖励 |
| RLVR | 可验证题目 | 最大化正确奖励 |

**讲稿要点**：

- 前两个阶段其实是同一个目标函数，只是数据换了。
- RL 换了目标：不再模仿，而是最大化奖励。
- 算力绝大部分花在 pretrain；后两个阶段数据少得多，却决定好不好用。

---

### S14 · Pretrain

**标题**：把互联网读一遍
**画面**：数据构成饼图：网页、代码、书、论文、对话。

**讲稿要点**：

- 目标只有一个：给定前文，预测下一个 token。
- 数据量万亿级 token；算力千到万卡、月级。
- 产出是 base model：它会续写，但不会"回答问题"。
- 这一步学到的是世界的统计结构，不是指令。

---

### S15 · 学到了什么，没学到什么

**标题**：一个会续写的模型

| 学到了 | 没学到 |
|---|---|
| 语法、事实、代码语法 | 指令跟随 |
| 常见推理模式 | 对话格式 |
| 文体与风格 | 拒绝与边界 |
| 部分世界知识 | 工具调用 |

**讲稿要点**：

- 你问 base model 一个问题，它可能续写更多问题。
- 所以需要 SFT。

---

### S16 · SFT

**标题**：还是预测下一个 token，只是数据换了
**画面**：`(指令, 回答)` 成对数据 → 微调。

**讲稿要点**：

- 目标函数没变，变的是数据：从网页文本换成高质量示范。
- 教的是格式、语气、何时调用工具、如何拒绝。
- 数据质量比数量重要。
- 结果：会回答问题了，但难题不一定做对——"像标准答案"不等于"做对"。

---

### S17 · RLHF

**标题**：按人的偏好调
**画面**：两个回答 → 人选更好的 → 训练奖励模型 → 优化策略。

**讲稿要点**：

- 优化目标是"人觉得好"：有用、无害、诚实。
- 不需要标准答案，只需要比较。
- 风险：奖励模型被攻破，模型学会谄媚。
- 这一阶段主要调风格与安全，不直接提升数学。

---

### S18 · RLVR

**标题**：让程序当裁判
**画面**：答案比对、单元测试、Lean 编译 → 0/1 奖励。

**讲稿要点**：

- Verifiable Rewards：奖励来自程序，不来自人。
- 数学：答案匹配，或形式化证明通过。
- 代码：测试通过、编译通过。
- 可以无限生成题目、无限尝试、自动判分。
- 这是数学与代码能力跃迁的关键机制。

---

### S19 · 为什么数学和代码适合 RL

**标题**：四个条件，它们全占

| 条件 | 数学 | 代码 |
|---|---|---|
| 对错可自动判定 | 答案 / 证明 | 测试 / 编译 |
| 可无限生成新题 | 改参数、改条件 | 改输入、改约束 |
| 难度可调 | 算术 → 竞赛 | 练习 → 竞赛 |
| 反馈即时 | 对 / 错 | 报错信息 |

**讲稿要点**：

- RL 最怕奖励稀疏且不可靠；这两个领域恰好相反。
- 代码的反馈不只是二元，还有具体错误位置，信息量更大。
- 所以它们是"AI 的训练场"，不只是"AI 的应用场景"。

---

### S20 · 代码 RL 如何提升推理

**标题**：它练的是四种习惯
**画面**：四象限。

1. **分解**：函数、模块 → 子目标
2. **验证**：测试 → 自己检查
3. **调试**：报错 → 定位 → 修正
4. **长程约束**：变量、类型、控制流 → 维持状态

**讲稿要点**：

- 这四件事，正好是"逻辑"的操作定义。
- 数学 RL 练演绎与精确性；代码 RL 练构造与纠错。
- 模型学到的是"先写步骤、再检查"的行为，不是某个定理。
- 这解释了为什么代码训练会迁移到数学和一般推理。

---

### S21 · 证据、边界与四个误解

**标题**：会迁移，但别夸大

| 误解 | 实际 |
|---|---|
| RL 能教新知识 | 主要是重加权已有能力、塑造行为 |
| 思维链越长越强 | 长链可能只是重复或绕圈 |
| benchmark 涨 = 更聪明 | 可能只是更会考试 |
| 算力够就行 | 奖励设计、数据质量才是瓶颈 |

**讲稿要点**：

- 观察到的现象：代码 RL 提升数学与通用推理；数学 RL 也提升代码。
- 机制上可解释：共享分解、验证、纠错技能。
- 必须打折：benchmark 污染、评测选择偏差、分布外失效。
- 结论：RL 训练的是**可验证任务上的搜索与纠错技能**，不是通用智能。

> ⚠️ 具体提升幅度需引用原始论文并标注数据集。

## 4. 使用（7 页）

### S22 · Prompt

**标题**：prompt 不是编程，是条件化

**讲稿要点**：

- prompt 是你这次传给模型的全部文本。
- 它不"执行指令"，它改变下一个 token 的概率分布。
- 模糊的 prompt 得到模糊的分布。
- 好的 prompt = 明确任务 + 给上下文 + 给验收标准。

---

### S23 · system / user / few-shot

**标题**：三种位置，三种作用

| 角色 | 作用 | 注意 |
|---|---|---|
| system | 身份、规则、边界 | 优先级高，但仍可被注入攻击 |
| user | 任务与材料 | 越具体越好 |
| few-shot | 用例子定义格式 | 例子比描述有效 |
| tool | 工具返回 | 当作不可信输入 |

**讲稿要点**：

- system 不是安全沙箱，只是权重更高的文本。
- few-shot 是最被低估的技巧：两个好例子胜过十句描述。
- 工具返回的内容可能包含恶意指令。

---

### S24 · Context

**标题**：窗口里到底有什么
**画面**：窗口分成五块：system、历史、检索、工具输出、当前问题。

**讲稿要点**：

- context = 这次前向传播能看到的全部 token。
- 上下文窗口是硬上限，超了必须截断或摘要。
- 所有"记忆"本质上都是把东西放回这个窗口。
- 关键指标不是长度，是**相关性密度**。

---

### S25 · Context rot

**标题**：越长越笨
**画面**：性能随上下文长度下降的曲线；标注 lost in the middle。

**讲稿要点**：

- 长上下文里，中间位置的信息最容易被忽略。
- 无关内容会稀释注意力，错误会被反复引用。
- 对策：摘要、检索、结构化、把关键信息放首尾。
- 成本也随长度增长，别把窗口当仓库。

---

### S26 · Memory

**标题**：模型没有记忆，记忆是产品

| 方式 | 做法 | 代价 |
|---|---|---|
| 重发历史 | 每次带上全部对话 | 贵、会爆窗口 |
| 摘要 | 定期压缩成要点 | 丢细节 |
| 外部存储 | 文件/数据库 + 检索 | 要设计、可能过期 |
| 工具记忆 | 让 agent 自己读写文件 | 最灵活，最易失控 |

**讲稿要点**：

- 参数在推理时不更新，所以"记住我"一定是外部机制。
- 三种方式可以组合。
- 核心问题是：什么该忘，什么该留。

---

### S27 · Agent loop

**标题**：让模型持续工作

```python
while not done:
    ctx = assemble(system, task, memory, last_obs)
    action = model(ctx)
    obs = environment.step(action)
    memory.append(obs)
    done = verifier.check(memory) or budget.exhausted()
```

**讲稿要点**：

- 模型负责提议，环境负责反馈，循环负责持续。
- 状态在外部：文件、数据库、工具，不在模型里。
- 为什么需要：单次生成无法验证，也无法完成长任务。
- 失败模式：死循环、上下文爆、工具误用。

---

### S28 · Harness

**标题**：同一个模型，为什么差一个数量级
**画面**：六组件表（工具、上下文、沙箱、控制流、验证、日志）。

**讲稿要点**：

- 模型是 CPU，harness 是操作系统。
- 能力 = 模型 × 上下文 × 循环 × 算力。
- 评估一个 AI 能否做某事，必须同时说明 harness。
- 报告结果时要写清工具、预算、重试策略。

---

## 5. 落地（3 页）

### S29 · 三个可用位置

**标题**：在内层，不在外层

| 位置 | 做什么 | 适用条件 |
|---|---|---|
| 数值实验 agent | 参数扫描、作图、拟合、检查 | 有明确脚本与验收标准 |
| 内层代理 | 单步力模型、稠密大气、辐射压 | 分布内、可校验 |
| 验证器 | Lean、符号计算、区间算术 | statement 可精确写出 |

**讲稿要点**：

- 共同点：可验证、可分解、在内层。
- 不适合：长期轨道预测、分布外外推、无验证器的开放问题。

---

### S30 · 一个 trace

**标题**：它实际是怎么干活的
**画面**：真实 agent 轨迹精简版。

```
读任务 → 写脚本 → 跑 → 报错 → 改 → 跑 → 画图 → 自查 → 报告
```

**讲稿要点**：

- 价值在循环里，不在单次生成里。
- 每一步都有可检查的产物。
- 失败与重试是常态，不是异常。

---

### S31 · 不该用的地方

**标题**：三条红线

- 长期轨道预测：混沌放大，没有廉价验证器
- 分布外外推：换 μ、换模型就失效
- 需要因果解释的结论：相关性不等于机制

**讲稿要点**：

- 不是"AI 不行"，是"这类任务缺少验证闭环"。
- 有验证器的地方，AI 可以很强；没有的地方，它只是自信的猜测器。

---

## 6. 结论（2 页）

### S32 · 因果链

**标题**：从 token 到定理

```
Token        → 模型能读
Pretrain     → 有先验
SFT          → 会按格式干活
RLVR         → 学会搜索与纠错
Context      → 拿到正确材料
Agent loop   → 能持续尝试
Verifier     → 保证正确
```

**讲稿要点**：

- 每一环都不可省略。
- 缺验证器 → 无法训练；缺 loop → 无法长程；缺 context → 没有材料。

---

### S33 · 三个判断

**标题**：值得做、别急着做、真正的瓶颈

- 值得投入：数值实验 agent、内层代理、形式化验证
- 暂不可靠：长期预测、分布外外推、无验证器的开放问题
- 真正瓶颈：数据质量、上下文设计、评测污染

**收尾句**：

> 它没有让创造性变得容易，它让"验证便宜"的领域变得可搜索。
